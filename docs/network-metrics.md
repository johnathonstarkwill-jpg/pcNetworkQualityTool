# 网络测试数据口径

应用只报告实测指标和采集状态，不生成网络质量分数、等级或业务适用性结论。

| 阶段 | 指标与来源 |
| --- | --- |
| 连通性 | TCP 控制端口连接是否成功；不能据此推断 UDP 或 ICMP 可达 |
| 空载延迟 | 系统 ping，约每秒一次 ICMP Echo；发包、响应、丢包数与丢包率，成功响应 RTT 的 min/avg/max/p95/p99 和样本数 |
| TCP 上行、下行 | iperf3 接收端平均吞吐量、接收字节和实测时长；单独列出发送端速率、发送端重传次数（可用时） |
| UDP 上行、下行 | 配置的目标速率；iperf3 接收端吞吐量、丢包数/总包数/丢包率、包间到达抖动；单独列出发送端速率 |

- 上行/下行以客户端为参照；Mbps 使用十进制，即 1,000,000 bit/s。
- 空载 ICMP RTT 在吞吐阶段之前采集；TCP 上行、下行各自并行采集负载 RTT。两者均为往返时间，不是单向时延。
- RTT 百分位使用最近秩法，丢失响应不进入 RTT 样本；样本少时 p95/p99 可能等于最大值。
- Windows ping 的 `time<1ms` 等响应以显示上界计入统计，并在说明中标明精度限制。
- ICMP 不响应可能与防火墙策略有关，不据此判定所有网络流量失败。
- TCP 重传次数不是丢包率；UDP 抖动不是 RTT。
- 缺失或不适用的数据显示为 `—`；真实测到的 0 保留。缺少必要指标、超时或断线的阶段标为“未完成”。
- 每个客户端、每个阶段串行执行。视频速率套件使用指定速率的 UDP 流，不模拟真实视频编解码或应用协议。
- 测试目标使用实际控制连接地址；报告记录各客户端使用的服务端地址。

服务端和客户端应同时更新，以使用相同的测试批次协议。iperf3 二进制须支持 `--json-stream`，现有最低要求见 `assets/iperf3/README.md`。

字段来源：[iperf3 官方文档](https://software.es.net/iperf/invoking.html)。

验证范围：macOS 本机回环 ping / iperf3，TCP 控制通道回归测试，以及 Electron 报告界面测试。Windows 的 ping 输出解析使用样例验证，尚未进行 Windows 实机和双机验证。

## 负载下延迟

- TCP 不设置目标速率上限；在接收到第一个数据流采样区间后，开始串行 ICMP 单次探测，每轮完成后间隔约 1 秒。
- TCP 结束即停止探测，取消仍在等待的 ping，不把负载结束后的响应混入统计。
- 分别列出上传负载、下载负载下的 RTT min/avg/max/p95/p99、样本数与 ICMP 丢包率。
- 平均 RTT 增量 = 负载平均 RTT − 同轮空载平均 RTT；p95 增量同理。增量允许为负；空载或负载无样本时显示 `—`。
- ICMP 被禁用时，吞吐数据继续保留，负载 RTT 单独显示未采集原因，不替换为 0。

## 吞吐趋势与稳定性

- 保存 iperf3 的完整逐秒区间（含开始、结束时间及最后不足一秒的区间），界面实时展示最近 120 个区间，完成报告保留完整趋势，Markdown 导出全部区间数据。
- 上行趋势使用客户端发送端速率，下行趋势使用客户端接收端速率；最终吞吐量仍使用接收端总量。观察端会在图表和统计表中明确标注。
- 根据实际区间时长，计算加权 min/avg/max、总体标准差和变异系数 `标准差 / 平均值 × 100%`；全为 0 时变异系数无定义，显示 `—`。
- “零吞吐”只统计实测 0 Mbps 的区间，列出发生次数、累计时长与最长连续时长。不能仅凭这个指标断言链路断开。
- 大于 0.01 秒的区间缺口单独计为“采样缺口”，不当作 0 Mbps；图表大于 0.02 秒的缺口不连线。
- 长趋势按横向区间保留最小值与最大值绘图，避免短暂下降被平均掉；导出的原始采样不做降采样。
- 每秒采样通过独立控制消息传输，避免长时间测试的最终单条报文超过协议长度限制。取消、断线时保留已经接收的部分采样，并标记未完成阶段。

所有套件均含 UDP 上行和下行；每个方向顺序执行，因此长时间套件的 UDP 总时长为单方向配置的两倍。UDP 是固定目标速率的质量测试；TCP 测量端到端可用吞吐能力，结果也受两端电脑性能和当时其他流量影响。
